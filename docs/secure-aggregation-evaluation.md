# RareLink 安全聚合选型与威胁模型

**状态：** P1-S06 方案选型已完成；生产启用与三设备验证未完成

**候选实现：** NVIDIA FLARE `FedAvgHERecipe` + TenSEAL 同态加密

**默认策略：** 失败关闭，未完成现场验收前不得启用或声称已运行安全聚合

## 1. 为什么 mTLS 不等于安全聚合

mTLS 保护站点与协调端之间的身份和传输，但协调端解密后仍可能看到每个站点的
单独模型更新。安全聚合的目标是进一步缩小协调端的可见范围。RareLink 选择
NVIDIA FLARE 已提供的同态加密联邦配方作为候选，不自行发明密码协议。

## 2. 威胁模型

候选方案主要缓解：

- 诚实但好奇的协调端查看单站明文更新；
- 单站更新在协调端聚合内存中的明文暴露。

候选方案本身不解决：

- 恶意客户端投毒；
- 全局模型发布后的成员推断和模型反演；
- 医院终端在加密前已经被攻破；
- 客户端串谋、密钥托管错误和可用性攻击。

因此 mTLS、样本级 DP-SGD、客户端本地裁剪、签名收据和模型发布核验仍必须保留。

## 3. 与当前更新防护的关键冲突

当前 `RareLinkUpdateGuardFilter` 在服务器聚合前检查有限值、范数、方向和重放，
并执行 L2 裁剪。真正启用同态加密后，服务器不应再获得可检查的明文张量。
生产方案必须把有限值检查和裁剪移动到签名的客户端执行边界；服务器只校验
身份、轮次、密文合同和聚合结果。不能同时声称“服务器看不到单站更新”又让
服务器对明文更新进行内容检查。

## 4. 本机运行时评估

运行：

```bash
.venv/bin/python scripts/evaluate_secure_aggregation.py \
  --sites hospital-a hospital-b hospital-c \
  --required-quorum 3 \
  --output artifacts/security/secure-aggregation-readiness.json
```

评估器检查 NVIDIA FLARE 配方和 TenSEAL 运行依赖，始终保持 `enabled=false`。
即使依赖齐全，状态也只会变为“可进入物理基准”，不会自动启用生产安全聚合。

## 5. 启用前验收门

1. 在 ARM64 DGX Spark 上安装并锁定兼容的 TenSEAL 版本；
2. 将裁剪和有限值检查移动到签名客户端边界；
3. 由医院密钥系统生成、托管、轮换和销毁 HE 上下文与密钥；
4. 测量精度、显存、内存、轮次延迟、密文尺寸和掉站行为；
5. 在三台物理 Spark 上完成加密轮次，并留存三站身份与结果收据；
6. 验证任一站点缺失时严格阻断，绝不从 3/3 静默降级；
7. 完成密钥托管、客户端串谋和恢复流程的安全评审。

只有以上证据同时满足后，P1-S06 才能从“方案已选型”升级为“物理安全聚合已验证”。

## 6. 结论

RareLink 已完成安全聚合的候选技术、威胁边界、架构冲突和验收门定义；当前
环境缺少 TenSEAL ARM64 运行时、三台独立 DGX Spark 及正式密钥治理，因此
保持失败关闭。TLS、仿真或单机三逻辑站点均不能替代安全聚合证据。
